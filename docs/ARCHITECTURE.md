# WealthView – Technical Architecture

**Version v1.24 · 2026-11-19** (the version number lives in one file, `version.js`, and is shown in the dashboard header, browser tab, intro, lock window, installer, `data.json`, READMEs and this document)

## 1. What it is, in three sentences
WealthView is a private, local web application: the dashboard is a single HTML page drawn with plain JavaScript (SVG charts, canvas map), and it is served to your browser by a small Python program (the standard-library `http.server`) that only listens on your own PC (`127.0.0.1:8780`). The Python side reads your files (GLS, PayPal, Example Fund CSV/PDF exports) into a local SQLite database (`wealthview.db`, filled automatically from your monthly downloads), adds Yahoo Finance quotes, Google News and the Coinbase API (through a small Node.js script), computes the dashboard numbers into one `data.json`, and hands it to the page only after the PIN was entered. The server is started by the desktop shortcut and stops itself when the browser page is closed, PowerShell scripts create the shortcut and the server task (the monthly reminder lives in the dashboard), and, since v1.16, two Inno Setup installers (public and private edition, section 15) set up a fresh PC; the older C# exe installer of v1.14 is superseded (section 9).

## 3. Processes: what runs where
```
Desktop icon ──► start-wealthview.ps1 ──► (background) start-lmstudio.ps1: starts LM Studio + Gemma 4 if not running
                                      ──► starts python server.py hidden (127.0.0.1:8780) if it is not up ──► opens the default browser (Firefox) on http://127.0.0.1:8780/
Browser page ──► heartbeat /api/hb every 10 s, goodbye /api/bye when the page is closed ──► the server ends itself when no page is left

Browser (dashboard)  ⇄  server.py  ──► refresh.py (subprocess, on demand + every 5 min "--quick" + automatically when new files appear)
                          │              ├─ db_import.sync: new files in the GLS / PayPal folders ──► wealthview.db   (files are only read)
                          │              ├─ Yahoo Finance, Google News  (urllib)
                          │              └─ coinbase_fetch.mjs (Node)  ──► api.coinbase.com
                          │            └─► data.json (+ daily snapshot into wealthview.db)
                          └─ /api/ask ──► ask.py ──► read-only SQL on wealthview.db  ⇄  LM Studio (127.0.0.1:1234)
```
* **Lifetime:** the server is *not* started at Windows logon. The desktop shortcut starts it (hidden, no window); it stops itself when the last WealthView browser page is closed: 12 s after the page says goodbye (so a reload does not stop it), about 2 minutes after a crashed browser stops sending heartbeats, and 5 minutes after start if no page ever connects. A sleeping PC does not count as "page gone". `config.json` → `"auto_stop": false` keeps the server running all the time. If the server is gone while a page is still open, the header light turns red; click the shortcut again.
* The 5-minute quick refresh only updates Coinbase and live prices (and saves today's snapshot); **PayPal, GLS and Example Fund files are looked at by a full refresh, but only new or changed files are actually read (v1.11)** – the Refresh button, or automatically when new files appear (next point).
* **Folder watcher (v1.08):** once a minute the server compares a cheap signature (file names, sizes, times) of the GLS and PayPal folders with the one stored in the database; when you drop in new downloads it runs a full refresh by itself (`config.json` → `auto_import`, `watch_seconds`). Only one refresh runs at a time; after a failed refresh the watcher waits 10 minutes, and when the folders still look changed after a good refresh (for example one unreadable file) it backs off 1, 2, 4, 8, 10 minutes instead of refreshing every minute (`jobs.extra_wait_after`).
* **LM Studio (v1.08):** `start-wealthview.ps1` calls `start-lmstudio.ps1` in the background. If nothing answers on port 1234 it starts the LM Studio server with the `lms` tool and loads the downloaded model that matches `ask.model_match` (default `gemma[-_ ]?4`, i.e. Gemma 4). If LM Studio already runs it is left alone. Log: `lmstudio_start.log`.
* Nothing is reachable from other computers: the server binds to `127.0.0.1` only and checks the `Host` header.

**Code layout (v1.14, sub-packages):** the `wealthview/` package is split into four layers, and `data/` into two sub-packages. Each module lives in exactly one place. Everywhere else in this document a module is named without its folder (for example `loaders.py`); this tree says where to find it.

```
server.py, refresh.py        launchers in the main folder (they only import from wealthview.app)
wealthview/
  common/     shared basics, import nothing from the other folders
              paths.py (folders, data_path, migrate_data_dir, version)   config.py (config.json, defaults)
              runcontext.py (RunContext, run_stage)   parse_cache.py   parsing.py (num, pdate, round2 ...)
              timeutil.py (month helpers, now, axis)   fileio.py   safenet.py   netlog.py   audit.py   bootstrap.py (start-up)
              types/ (TypedDicts by domain: bookings, depot, status, research, network, datajson)
  data/       getting data in and turning it into clean records
    ingest/   files, database and web lookups
              db_schema.py  db_import.py  db_queries.py  loaders.py  gls_parse.py  paypal.py  sources.py  quotes.py  company_info.py  logo_fetch.py  logos_online.py
    finance/  the money model (imports ingest/, never the other way)
              bookings.py  categories.py  ownaccounts.py  gls_block.py  lots.py  positions.py  models.py
  analysis/   reading the clean data and producing insights
              totals.py  analytics_run.py  quick.py  alerts.py  gaps.py  unusual.py  insights.py  analytics.py  research.py  ask.py
  app/        the two programs
              refresh.py (data pipeline: runs the STAGES list)   refresh_stages.py (the I/O stages)
              server.py (routing + handlers)  auth.py (PIN, tokens)  lifetime.py (tab watchdog)  jobs.py (refresh subprocess, folder watcher)
```

The folders form layers. An arrow means "may import from": `app -> analysis -> data (finance -> ingest) -> common`. Nothing goes the other way, so there are no import cycles (checked by `tests/test_layers.py`, which reads every import, also the ones inside functions). If you add a module, put it in the lowest layer that has everything it needs. Inside a folder, modules import each other with `from .x import ...`; across folders with `from ..common.config import ...` (one more dot inside `data/ingest` and `data/finance`: `from ...common.config import ...`). Tests and launchers use full paths such as `from wealthview.data.ingest import db`. `paths.BASE` is the folder above `wealthview/` (the project root), so `config.json`, the web files and `data/` are found as before. The old names `wealthview.core`, `wealthview.db` ... no longer exist; use the paths above.

**Run state (server):** everything the server changes while it runs hangs on one object, `server.STATE` (`auth.AuthState` = session tokens + PIN counter and their locks, `lifetime.PageLife` = open browser pages, `LiveQuotes`, `jobs.Refresher` = the one-at-a-time refresh lock). `common/config.py` is the only module that reads `config.json` (again when the file changes; treat the dict as read-only). Domain modules ask it for one setting (`setting()`, `section()`, `cfg_value()`, `oneoff_threshold()`, `own_names()`); only the app layer passes the whole dict around (folder watcher, update reminder, database sync). `common/bootstrap.py` is the one start-up routine (logging, data-folder migration, connection log) that `server.main` and `refresh.run_cli` call first.

**Layout (v1.14):** the code is the `wealthview/` package; run `python server.py` / `python refresh.py` from the main folder. `config.json`, `examplefund.json` and the web files stay in the main folder; everything the program writes lives in `data/` (`paths.data_path()`). On the first start `paths.migrate_data_dir()` moves the old files there and keeps the originals in `_pre_data_dir_backup/` (nothing is deleted). Checks: `python -m unittest discover -s tests -t .`, `python -m pyflakes server.py refresh.py wealthview tests`, `python -m mypy wealthview server.py refresh.py`, `python -m bandit -q -r wealthview server.py refresh.py`.

| any other `/api/…` path | token | deny by default (v1.13): an unknown or new route answers 401 until it is added to `PUBLIC_API` on purpose |
| `/api/netlog` | token | WealthView-only connection log for the map; with `?wait=1&sig=…` it is a *long poll* that answers the moment a new connection starts |

**Status contract:** `401` locked (no valid session), `403` wrong `Host`, `404` unknown route (for a signed-in session) or missing file, `429` PIN lock-out. A domain failure (empty question, database or lookup error) answers `200` with `{ok: false, error: ...}`, because `wv.js` `api()` treats any other non-2xx as a link error. The JSON routes (lookups, `/api/netlog`, `/api/unusual_seen`, `/api/ask`, `/api/ask/status`) use `api_boundary`: every answer is `{ok: bool, error?: str, ...}` (`ok` is added when a handler leaves it out; an answer that carries an `error` is `ok: false`). Two routes answer with a plain document on success: `/api/real` (`data.json`) and `/api/src_logos` (the logo map); their failures use the same `{ok: false, error}` shape, which `wv.js` already checks (`d.error`, `!lg.error`).

## 5. Dashboard (front end)
* `wv.js` is one IIFE: state `S`, panel builders (`pDepot`, `pGross`, `pMap`, …), `renderAll()` writes all five columns, `POST` callbacks draw charts after the HTML exists. `insights.js` (`window.WVI`) adds the "Over time" box, the digest items for Smart suggestions, the database line in System status and the Ask bar (v1.12: a normal-flow element directly under the network box in the centre column, same width as that box, re-attached after each render, so it never covers a box).
* Charts: `drawTS` (time series, SVG), `posChart` (price + your buys/sells; with more than 30 trades the small buys are not drawn as markers), `donut`, treemap heatmap (`openHeat` + `squarify`). The heatmap switches the box (or the open window) **in place**; `S.heatOn[id]` remembers which boxes show the heatmap.
* Colour/glow logic: `glowOf` / `glowPass` (green/red glow, breathing at ±100 %). Box groups get a coloured frame/top bar/title through `data-grp` (`GRP` map in `wv.js`, CSS in `wealthview.html`).
* Privacy blur: `.priv` blurs amounts; boxes marked `NB` (securities allocation, spending, top pay, recent + unusual bookings) stay readable, except the securities total inside the allocation donut (`text.amt`).
* Layout (v1.07): `layoutCenter()` measures the gross-assets chart box, makes it 30 % taller and shrinks the ring by the same height (re-run on resize). Pop-ups (v1.17) are half the screen wide and as tall as their content (section 14b); the position pop-up is a CSS grid (`.pp.pos`) whose purchase table merges small lots into one row until everything fits without scrollbars.
* Unusual bookings: unseen rows and the box blink red; a click (or "Dismiss all") stores the booking key in the database through `/api/unusual_seen` (v1.11; `localStorage` `wv_unusual_seen` is only a cache), so it stays dismissed after a refresh or restart.
* Recent bookings: a click opens `openBookings(name)` with the history from `data.gls.bookings[name]` (newest 500 per company since v1.08; the name is the one shown in the list).
* Over time + Ask (v1.08): see sections 13 and 14.
* Map: land shapes decoded to a 360×180 raster and sampled into dots; arcs, particles and ripples are drawn with `requestAnimationFrame`. A new connection triggers a white burst ring on its node.
* Demo mode: invented numbers from `wv_demo.js` (and `demoInsights` for the Over-time box); real data is never embedded in the HTML. Since v1.12 the position, coin and company pop-ups in demo mode show canned, clearly labelled EXAMPLE research, headlines and company facts from `wv_demo.js` (no lookups), and the Example Fund box shows nine invented example companies.

## 6. Data pipeline
0. `ingest/db_import.py` – `sync()` imports every new file from the watched folders into `wealthview.db` first (section 12); the bookings are then read back from the database in the same shape `loaders.load_gls()` returns, so the steps below did not change. If the database cannot be used the files are read directly as before. **The CSV fallback is intentional:** the database is the primary store; `loaders.load_gls` / `paypal._scan_paypal_files` are a deliberate fallback for an unusable or empty database (pinned by tests in `tests/test_refresh_pipeline.py`). Its file discovery is narrower than `db_import.watched_files`: it reads only the GLS DATA folder, not the older exports in the folder above it.
1. `common/` – `config.py` (`load_config()` with reload on change, `cfg_value`, defaults), `paths.py` (`data_path()`, `migrate_data_dir()`, `version()`), `runcontext.py` (`RunContext` = status and alerts of one run, `run_stage()` = the one helper that runs an optional stage and turns a failure into a log line plus a status line or alert), `parse_cache.py`, `parsing.py`, `timeutil.py`, `fileio.load_json_cache()`. `ingest/loaders.py` – the source loaders (GLS, depot, Coinbase, Example Fund; IO only), `ingest/gls_parse.py` – the pure parsers, `finance/gls_block.py` – `build_gls_block` and the booking analysis; `types/` (`bookings.py`, `depot.py`, `status.py`, `research.py`, `network.py`, `datajson.py`) – TypedDicts for bookings, depot positions, trades, holdings, source status, alerts and every block of `data.json`. (The old stand-alone `main()` / `load_paypal()` of the HUD era were removed in v1.09; `refresh.py` is the only pipeline.)
2. `app/refresh.py` – only orchestrates: `main()` runs the explicit `STAGES` list (each stage names the `Run` values it needs and provides; `check_stage_order()`, run by the tests, fails when the order is wrong), `quick_main()` calls its helpers in order. The work is in `app/refresh_stages.py` (database, bookings, depot + trades, snapshot), `analysis/totals.py` (totals, KPIs, runway), `analysis/analytics_run.py` (outside data + analytics) and `analysis/quick.py`; `finish_data` runs the optional steps through `run_stage`. The pipeline parses GLS bookings (cash flow, categories, merchants, securities trades, per-company booking history `group_bookings`), depot export, PayPal (newest balance row; for rows in the same second the later one wins), Example Fund; adds Yahoo quotes/history, Coinbase holdings; builds the back-cast asset-class history; records the daily snapshot and `data.insights`; writes `data.json`.
3. `research.py` – per-security research on click (trend, momentum, RSI, 52-week range, analyst consensus, headline tone → 0–100 meta-score).
4. `logos_online.py` – company logo lookup (Wikidata → verified domain guess → icon services); only the company name leaves the PC.
4b. **Company enrichment, who owns what:** `logos_online.py` finds a missing logo on the web (on click), `logo_fetch.py` builds the merchant/coin logos into `src_logos.js` during a refresh, `company_info.py` gives the Wikidata profile and news of one company, and `research.py` gives Yahoo prices, analysts and news scoring for one security. They share the Yahoo helpers in `quotes.py` and the RSS/URL helpers in `safenet.py`; they stay separate modules.
5. `sources.py` (v1.11) – update reminder: a monthly source is *due* when its newest data is older than the last day of the previous month minus 3 days; Example Fund is due after 135 days. Shown as a chip in the top bar and as the first Smart suggestion; since v1.12 every entry also carries the real `folder` and file `pattern` to drop new files into (GLS DATA folder for `Umsaetze_*.csv` and `Depotbestand_*.csv`, the PayPal folder for `Download*.CSV`, the Example Fund report folder for the quarterly PDF), shown in the chip's pop-up.
6. Parse cache (v1.11) – `parse_cache.cached_parse()` keeps the parsed depot export, Example Fund files and CSV fallbacks in `parse_cache.json`, keyed by file path, size and modification time, so "Refresh data" only reads files that are new or changed; the database import (`db_import.sync`) is skipped when the watched folders did not change.

## 7. Network log for the map (`netlog.py`)
* `install()` patches `urllib.request.OpenerDirector.open` in every WealthView Python process (server and `refresh.py`), so each outbound request is appended to `netlog.jsonl` as *host + time* when it **starts**; the Coinbase call is logged by `loaders.py`.
* Only connections started by WealthView are recorded – not a system-wide monitor, never the full URL, never content. The Ask box talks to 127.0.0.1 only and is not part of the log.
* Place of a host: cache `netgeo.json` → offline DB-IP file (if the `maxminddb` package and a `dbip.mmdb` exist, read-only) → ip-api.com (sends only the server IP) → small built-in table.
* Live update: the page keeps one request open (`/api/netlog?wait=1`); the server checks the log file's size/time every 0.3 s (one `stat` call – negligible CPU) and answers immediately when it changes.

## 8. Security model
* Convenience PIN (**v1.13:** salted PBKDF2-SHA256 in `config.json` -> `pin_hash`; v1.14: the old unsalted `pin_sha256` is no longer accepted, see PIN setup below), token in `X-WV-Token`, lock-out after failed tries. **v1.09:** one gate (`_blocked`) runs before any handler. **v1.13: deny by default** – every `/api/` route needs a session unless it is in `PUBLIC_API` (`ping`, `hb`, `bye`, `unlock`); `LOCKED_PATHS` only lists protected static scripts. `audit.py` appends unlocks, failures, lock-outs, refreshes and question lengths to `audit.log` (never PIN, token or question text; capped at 256 KB). Request bodies that are not JSON objects count as empty; expired tokens are purged at each unlock, `/api/lock` revokes a token, and the PIN counter and token table are guarded by the two locks of `auth.AuthState`. It is not file encryption – and `wealthview.db` holds all your financial data unencrypted.
* **PIN setup (v1.14):** only the salted `pin_hash` is accepted. The old unsalted `pin_sha256` login and its automatic upgrade were removed. If `config.json` has no `pin_hash`, nobody can unlock: the server logs the problem at start and `/api/unlock` answers `{ok: false, error: ...}` with the text that tells the owner to run `python server.py --set-pin` (it asks for the PIN twice, hidden, and writes a salted `pin_hash`; an old `pin_sha256` is dropped). Wrong tries are only counted when a PIN is set.
* **Outbound requests (v1.09):** all web access goes through `safenet` – only `http`/`https` URLs are opened (no `file:` or custom schemes), RSS/XML with a DTD or entity declarations is refused, and ignored errors are logged at debug level (logger `wealthview`) instead of vanishing. `bandit -r wealthview server.py refresh.py` reports no issues.
* Source folders (GLS, PayPal, Example Fund) are only read. WealthView writes only inside its own folder: the `data/` subfolder (`data.json`, `wealthview.db`, caches, `netlog.jsonl`, `netgeo.json`, `audit.log`), plus `logos/`, `src_logos.js` and `lmstudio_start.log`.
* Coinbase key: view-only, Windows user variables, never in a file or in this documentation.
* The installer contains `config.json` (PIN hash, paths): keep it private.

## 12. Database and automatic import (v1.08)
* **File:** `wealthview.db` in the `data/` subfolder of the WealthView folder (v1.14; older versions kept it next to the program files) (SQLite, default journal mode so no extra files appear next to it in OneDrive). The imported tables can be rebuilt from your downloads, **but the daily snapshots exist nowhere else** – keep the file in your backups.
* **Tables:** `bookings` (GLS accounts and card; unique key = account, date, amount, balance after booking, first 80 characters of the purpose, first 30 of the counterparty), `paypal_tx` (no e-mail or postal addresses are stored), `depot_positions` (one row per position per Depotbestand export date), `trades`, `snapshots` (day, scope, key, value, extra; scopes `total`, `class`, `position`, `coin`), `spending` and `monthly` (classified spending and monthly income / expense / category totals, rebuilt on every full refresh), `files` + `file_seen` (import log), `meta`.
* **Import rules (`db_import.sync`):** watched = GLS `*Umsaetze_*.csv` and `Depotbestand_*.csv` in the DATA folder, GLS `*Umsaetze_*.csv` in the folder above it (older years), PayPal `Download*.CSV`. A file is recognised by its sha256, so a renamed copy is skipped as a duplicate; an unchanged path/size/time is skipped without being read. Overlapping exports are merged row by row. A file that cannot be read right now (for example a OneDrive file not downloaded yet) is reported and retried next time; a file in an unknown format is reported once and remembered. The source folders are only ever read.
* **Gaps:** `db_queries.coverage` lists per account the first/last booking and months without any booking (busy accounts only); these become warnings next to the existing data-gap alerts. System status shows rows, date range, last import and recorded days.
* **Snapshots:** every full or quick refresh writes today's totals, asset classes, securities positions and coins (`record_snapshot`); the last write of a day wins. `history.json` is read once to seed the first days.

## 14. Ask box (v1.08)
* **Flow:** page → `POST /api/ask` (PIN session) → `ask.answer()` → LM Studio `/v1/chat/completions` on 127.0.0.1. The model gets the table layout and rules and answers either with one sql code block (a single SELECT) or with the final text. The server runs the SELECT and sends the result back (at most 4 queries). The plain-text protocol needs no tool-calling support, so any model works; Gemma 4 is preferred (`ask.model_match`).
* **Empty replies (v1.17):** `lm_chat` asks for `ask.max_tokens` (default 4096; it was 900). A "thinking" model such as Gemma 4 spends tokens on reasoning that LM Studio stores in `reasoning_content`; with a small allowance `message.content` stays empty (`finish_reason: length`) and the box used to print "No answer.". `lm_chat` now raises `EmptyReply` (reply with only `<think>` text counts as empty), and `answer()` returns `ok:false` with a plain message plus `detail` (finish reason, reasoning length, token limit). Tests: `tests/test_ask_empty_reply.py` (fake LM Studio server).
* **Guard (server side, never trusted from the model):** read-only connection (`mode=ro`, `query_only`), SQLite authorizer that allows only SELECT / READ / FUNCTION / RECURSIVE, internal tables (`meta`, `file_seen`) unreadable, one statement, 100 rows and 6,000 characters per result, 3 s time limit. Anything that is not a SELECT is never run. The page lists the queries used under every answer so you can check the numbers.
* **Privacy:** question, portfolio summary and query results go only to the model on your own PC. **v1.15:** the model may ask for a web search (`SEARCH: words`); `analysis/advisor.py` then fetches a public search page (DuckDuckGo HTML) with only those words, feeds the top results back and returns them as `sources` (title + link). The prompt tells the model never to put balances or personal data into search words. The portfolio summary (`advisor.portfolio_summary`, from `data.json`) lets it answer about the whole portfolio and give investment views; lookups (SQL + searches) are capped at `ask.max_rounds`.
* **Settings:** `config.json` → `ask` (`url`, `model` or `auto`, `model_match`, `start_lmstudio`, `lms_path`, `max_rounds`, `max_tokens` (v1.17, default 4096), `timeout_s` (default 180)).

## 14b. Layout rules for the chat bar and pop-ups (v1.17)
* **Ask bar:** `insights.js place()` makes `#chat` the last flex item of `#center` when the grid is `position:fixed` (wide screens) and moves it behind the grid when the page stacks. `renderAll()` detaches and re-attaches it so typed text survives a redraw. `layoutCenter()` lets `#ringWrap` shrink (`flex:0 1 auto`, minimum 12 rem) so the centre column can never grow past the grid. Cause of the old overlay: `#ringWrap` was `flex:none` at 43.4 rem, so on shorter screens the column overflowed under the fixed bar.

* **Pop-ups (`.modal`, `.modal.fit`):** `width:min(98vw, max(50vw, 52rem))`, `height:auto`, `max-height:96vh`; charts inside are `clamp(16rem,44vh,34rem)` high instead of filling the window.
* **Example Fund overview:** `wfgLayout(n, width)` (pure, tested by `tests/wfg.test.js`) uses 4 rows (`WFG_ROWS`) for 4 or more companies, columns = ceil(n/4), cell mode `full` / `mid` / `sm` by cell width; the window grows to the cards, nothing scrolls.

## 15. v1.16 installers and profile

* **Profile (`wealthview/common/profile.py`).** `data/profile.json` = `{edition: public|private, tier: ultrawide|desktop|laptop|compact, asset_classes, sources[{kind, folder, entity, mapping}], modules{examplefund, wiwin, loan, apartment}, tax_country, home{lat, lon, label}, chat, jarvis_url}`. * **Tiers and modules.** The tier is the widest layout the installer's PC check allows (`compact` 1 column, `laptop` 2, `desktop` 4, `ultrawide` 5); the page never uses more columns than its window gives (`layout.js` `tierOf`). Asset classes (cash, securities, privateEquity, realEstate, crypto) and modules are switched on only by sources that exist; the engine derives them conservatively from the source kinds (GLS and PayPal give cash, a depot gives securities, Coinbase gives crypto; none of the four optional modules is on by default).
* **Box registry (`layout.js`).** `WVL.BOXES` lists every dashboard box with its column and its `needs` (asset classes, modules, `chat`). `pickBoxes(profile, viewport)` returns the ordered box ids, `place()` the boxes per column, `columns()` the column count, `domIds()` the element ids `wv.js` writes. For the legacy profile on 5120x1440 the result is the v1.15 order (columns 5, 2, 3, 1, 4), pinned by `tests/golden_layout_v115.json`. With no asset class at all the page shows one empty-state box. Node tests: `tests/layout.test.js`.
* **Source plugins (`wealthview/data/ingest/plugins/`).** A plugin has `name`, `detect(path, head_bytes) -> confidence` and `parse(path)`; `REGISTRY` holds `gls`, `gls_depot`, `paypal`, `coinbase` and `csv`; `detect_best(path)` reads at most 4096 bytes and answers only above 0.5. The `csv` plugin never wins detection (confidence at most 0.3): it is used when a source of kind `csv` carries a column mapping (`{date, amount | debit/credit, text, counterparty, date_format, delimiter, decimal, encoding}`), or a guess from common German/English header names (`csv_generic.py`). The wizard has no mapper screen (ruling R31); unknown CSVs are listed as skipped. **Importer settings (R34).** `profile.sources` is shown by the app; the importers read `config.json`. `apply` (`installers/engine/wvsetup/importcfg.py`) derives `gls_dir` (first `gls` folder, else the first `gls_depot` folder), `paypal_dir` (first `paypal` folder) and `csv_sources: [{folder, entity, mapping}]` (all `csv` sources) from the answers and merges them into `config.json` (atomic, other keys kept). A key that already has a value is never replaced, so a private bundle's `config.json` wins; the JSON output of `apply` lists `import_config` and `warnings`. **Limits (reported as warnings, not imported):** only one GLS folder and one PayPal folder are read; a depot folder different from the GLS folder is not read (`Depotbestand_*` files are read from the GLS folder); `coinbase` has no folder. **Generic CSV:** `db_import.watched_files` also yields `("csv", path)` for every `*.csv` in each `csv_sources` folder that is not a GLS/PayPal file by name (`Umsaetze_*`, `Depotbestand_*`, `Download*`); `import_csv_file` writes the plugin rows into `bookings` with `account` = the entity label, `kind` `giro`, `iban` = pseudo id `CSV-<ENTITY>`, no balance and no category (the categoriser runs later in the pipeline, as for GLS rows); a CSV without a mapping that the header guess cannot fill is recorded as skipped. The refresh reads flows, income and expenses from the `bookings` table (`db_queries.load_gls_rows`), so CSV bookings appear in every view built from bookings; the GLS-only file stages (`loaders.load_gls` fallback, depot, `gls_files` status) still look only at `gls_dir`. Sync counts CSV bookings in `new_bookings`; `new_files[].source` is `csv`.
* **The installers tree.** `installers/engine/wvsetup/` (the engine: `cli.py`, `hwcheck.py`, `scan.py`, `apis.py`, `password.py`, `bundle.py`, `jarvis.py`, `lmstudio.py`, plus `assets/hud-wealthview.js`), `installers/iss/` (Inno scripts `wealthview-public.iss`, `wealthview-private.iss`, shared `wealthview-common.iss.inc`, helper `run-engine.ps1`, wizard images), `installers/build/` (`build-installers.ps1`, `build_dryrun.py`, `make_payload.py`, `leakscan.py`, `allowlist.txt`), `installers/private/` (examples and READMEs; the real overrides, terms and profile are git-ignored), `installers/templates/`, `installers/tests/`. Flow: wizard pages (privacy promise, PC check, residence, sources, Ask box, password, optional J.A.R.V.I.S., install) -> engine CLI (`check`, `scan`, `check-password`, `verify-bundle`, `apply`, `uninstall`) -> `apply` writes the install.
* **Engine CLI and `answers.json` (ruling R3).** Every command prints exactly one JSON object and exits 0 or 1; no traceback, no secret. `apply <answers.json>` takes `{edition, install_dir, password, tier, tax_country, home, sources[{kind, folder, entity, mapping}], chat{enabled, model}, jarvis{enabled, dir}, bundle_path}`; unknown keys are refused; the file is deleted in a `finally` block. Order: validate -> (private) decrypt the bundle into a temp folder to check the password -> `config.json` (seeded from the bundle's, else `config.default.json`) with the password hash -> `data/` -> copy bundle files that do not exist yet -> `profile.json` -> optional Jarvis patch -> `data/install.json`. An existing `profile.json` is kept and only tier, chat and `jarvis_url` change (R28); data files are never overwritten (R27). The engine creates no shortcuts (Inno does, R26).
* **Password path.** One free-text password per install (NFC, 4 to 1024 characters; since 12 Nov 2026 a 4-digit PIN is allowed. The private installer bundle is encrypted with this password via scrypt + AES-GCM, so a very short password can be guessed offline by anyone who gets the .exe: use a longer one for the private build), stored as the salted PBKDF2 hash `pin_hash` (the config key keeps its old name; `auth.hash_pin` NFC-normalises). It never travels on a command line or in a file: the wizard sets the environment variable `WV_SETUP_PW` only around the start of `run-engine.ps1`, which removes it and pipes `{"password": ...}` to the engine's stdin. The build uses `BUILD_BUNDLE_PW` in the same way for the bundle password. The dashboard unlock sends it once in the body of `/api/unlock`.
* **Private bundle (`bundle.py`).** `WVB1` file: AES-256-GCM over a tar of the private files (`config.json` without the PIN hash, `examplefund.json`, `wf_data.js`, logos, optional `private_profile.json`; never a database), key from scrypt (n=2^15, r=8, p=1) over the NFC password, header bound as associated data, all failures are one `WrongPassword`. It is used by the private installer only (the setup extracts it once; the file is not kept in the app). The `cryptography` package is imported lazily, so the public edition and the app never need it.
* **Public payload, allowlist and leak scan.** `make_payload.py` copies only the files matched by `allowlist.txt` (program code, `vendor/`, icons, scripts, `config.default.json`); `NEVER_PUBLIC` patterns, databases, logs, `.pyc`, executables and any symlink are refused. `leakscan.py` then scans the payload, the engine copy and the installer scripts (`.iss`, `.inc`, `.ps1`) for the owner's private terms (a file outside the repository and OneDrive, ruling R33: `%USERPROFILE%\WealthView-private-build\private_terms.txt`; hits are reported as `term#N`, never the term) and for built-in patterns (IBAN, e-mail, user paths, `pin_hash`). ISCC only reads the scanned copies; any hit stops the build and no exe is written. It does not detect escaped or encoded forms of a term (documented in the script).
* **First-refresh logo lookup (ruling R29).** A new install has no logo cache, so `logo_fetch.py` looks up merchants online, fail-closed: a name is sent only if its category is on a commercial allowlist or it has a business keyword, and it passes the special-character, person-shape and generic-booking-word filters (max 60 lookups per refresh); config `logo_lookup: false` turns it off. Cost: some real brands (two-word names, single words in non-commercial categories) get no logo.
* **J.A.R.V.I.S. patch (`jarvis.py`).** Finds the HUD folder (registry and usual places) and adds a WealthView button to `hud.html`: bytes only, original saved as `hud.html.wealthview-backup`, one block between `<!-- wealthview:begin -->` and `<!-- wealthview:end -->`, a state file with the original hash, atomic write last, local addresses only. `unpatch` restores the original bytes (or removes only the block if the page was edited since). A HUD that already has its own `#wvBtn` gets no second button.
* **LM Studio planner (`lmstudio.py`, `hwcheck.py`).** Pure functions: the PC check decides if the Ask box is feasible; `pick_model` chooses Gemma 3 4B/12B/27B by video memory (6 to <10 GB, 10 to <16 GB, 16 GB or more; with no usable GPU 12B if RAM is at least about 31.5 GB); `plan_commands` returns the `winget` and `lms` commands the wizard runs visibly; `write_ask_config` records the model in `config.json` and sets `chat` in the profile. `lms` only works after LM Studio ran once.
* **Build pipeline.** `build-installers.ps1 -Edition public|private` -> `build_dryrun.py`: validate `version.js` (the only version source; the exe version comes from it via `/DAppVer`) -> stage the payload and the engine copy -> leak scan -> (private) assemble and encrypt the bundle, then decrypt it again to verify -> ISCC on the staged scripts -> move the exe to `installers\dist` (public) or `installers\private` (private; the build only warns when that folder is under OneDrive, because the exe holds just the encrypted bundle, never a database; `-OutDir` chooses another folder) -> staging removed in every case. `-DryRun` stops before ISCC. Tests use a fake ISCC; `installers/tests/test_e2e_public.py` runs build -> payload -> `apply` -> installed `server.py` -> `layout.js` on invented data.
* **Superseded v1.14 installer.** `build_installer.ps1`, `installer.cs` and `uninstaller.cs` still sit in the main folder. Nothing under `installers/` or in the app refers to them; only `README.md` and this document mention them, and `installer.cs`/`build_installer.ps1` refer to each other. They are not part of the v1.16 public payload (not on the allowlist) and were not deleted; they are replaced by the Inno installers. `install_tasks.ps1` is in the payload but unused by the new installer (Inno creates the shortcuts).

## 16. Sources and accounts (v1.19)
First stage of the flexible setup (project docs "WealthView - flexible setup (any wealth setup) - design spec" and "WealthView flexible setup - implementation plan"). The dashboard and `data.json` are unchanged in this stage.

* **Two lists.** `sources` = one row per thing the user set up (`name`, `section` bank / investment / crypto, `source_type` folder / api / manual, `folder`, `connector`, `reader`, `options` JSON, `active`, `legacy_key`). `accounts` = one row per account found inside a source (`source_id`, `name`, `kind` bank / card / depot / crypto / property / loan / fund / other, `ident` = IBAN or another stable id, `currency`). One folder can hold several accounts, which is why the two are separate. Code: `data/ingest/db_accounts.py` (`add_source`, `list_sources`, `set_source_active`, `account_for`, `list_accounts`, `kinds_with_data`); types in `common/types/accounts.py`.
* **Links.** `bookings.account_id`, `paypal_tx.account_id` and `depot_positions.account_id` point to `accounts.id`; `files.source_id` to `sources.id`. `depot_positions` has the key `(account_id, asof, wkn)`, so two depots can hold the same security on the same day.
* **Schema version.** `meta.schema_version`: 1 = the shape up to v1.18, 2 = sources and accounts. A new, empty database starts at 2. `db_schema.ensure_schema2()` adds the new columns; `schema_version()` reads the number.
* **Upgrade (`db_migrate.upgrade`).** Run by `refresh_stages.upgrade_db()` at the start of every refresh while the database is at version 1. Order: backup copy `data/wealthview.db.pre-accounts.bak` (SQLite backup API, kept if it already exists) -> one explicit transaction (`BEGIN IMMEDIATE`): new columns, one source per folder that `config.json` names (`gls_dir`, `paypal_dir`, `csv_sources`: the folders the old version imported; `profile.json` only supplies the user's name for a folder; a Coinbase source when there are coin snapshots), one account per IBAN (card accounts keep kind `card`; rows without IBAN share one account), PayPal and depot accounts, `depot_positions` rebuilt, version set to 2. Any error rolls everything back; the refresh continues in the old shape and System status shows "database upgrade postponed: <reason>". Rows whose folder is unknown go to a source named "Imported bookings". Sources made by the upgrade keep the old reading rules (`include_parent` for the bank folder, no sub-folders), so exactly the same files are read as before.
* **New installs (`db_migrate.seed`).** A version-2 database without sources gets them once from `config.json` and every folder of `profile.json` (the installer still writes folders there), with sub-folders on. After the upgrade or this seeding, changing `gls_dir` / `paypal_dir` in `config.json` no longer changes what is imported into the database (the file-based fallbacks in `loaders.py`, `paypal.py` and the reminder in `sources.py` still read those keys until v1.22).
* **Import (`db_import`).** `watched_entries(cfg, sources)` lists the files of all active folder sources by their `reader`: `gls` (bank booking and depot exports), `paypal`, `csv` (generic mapper), `auto` (nothing yet; the automatic reader comes in v1.20). Sub-folders are read when `options.subfolders` is not false: 4 levels, at most 500 folders per source, hidden folders and links skipped. A file reachable from two sources belongs to the first. A source whose folder is missing is reported by name in the sync report and the other sources continue; the folder signature contains a "missing" line, so a folder that returns is noticed without causing a refresh every minute while it is away. `sync()` gives each imported row its account. An IBAN is always one account, whichever source's file delivers its rows. A csv source keeps its original `entity` in `options` (the id of its rows is derived from it). A database with an empty `sources` table (or still at version 1) reads the `config.json` folders as before; one whose sources are all switched off reads nothing.
* **Shown.** `data.db.counts.sources` / `.accounts` (active ones) appear in the database line of System status; that line no longer names a bank. The Ask box may read `sources` and `accounts`; `formats` and `questions` are hidden from it.
* **Tests.** `tests/test_db_accounts.py`, `tests/test_db_migrate.py` (with `tests/v1db.py`, a database in the v1.18 shape with invented rows), `tests/test_sync_sources.py`, additions in `test_db.py`, `test_ask.py`, `test_refresh_pipeline.py`.

## 17. API connections and stored keys (v1.21)
* **One table of services (`data/ingest/connectors.py`).** `CONNECTORS`: id, label, the sections it may be used in (bank / investment / crypto), the fields the setup screen asks for (`secret` fields are password inputs), `ready` (the refresh really reads it) and the environment variables that can supply the keys instead (Coinbase, older setups). Crypto: `coinbase`, `binance`, `kraken` (ready). Bank and investment: `fints` (not ready: only the connection details are stored, no PIN is asked for; `fints_sync.py` is still not connected to the refresh).
* **Where keys live (`data/ingest/keystore.py`).** One credential per place in the Windows Credential Manager, target `WealthView-API-<sources.id>`, value = JSON of the typed fields (`fints_sync.cred_write` / `cred_read`, plus `CredDeleteW`). Nothing about keys is written to `config.json`, the database, `data.json`, the audit log or a log line; `/api/setup/state` only carries `has_keys` per place, `connectors` (the public part of the table) and `keys_possible`. Tests set `keystore._memory` to a dict.
* **Setup actions (`db_setup.source_action`).** `add` with `source_type: "api"` checks that the connector fits the section, needs every field (unless the connector's environment variables are set), creates the place and stores the keys in the same transaction (a failed store rolls the place back). New action `keys` (id, keys) replaces the stored keys. `delete` of a place without accounts also deletes its credential.
* **Readers (`data/ingest/exchanges.py`).** `binance_balances`: signed `GET api.binance.com/api/v3/account` (HMAC-SHA256, header `X-MBX-APIKEY`), free + locked per coin, `LD…` (flexible Earn) folded into the coin. `kraken_balances`: signed `POST api.kraken.com/0/private/Balance` (HMAC-SHA512 over path + SHA-256(nonce + body)), Kraken codes mapped (`XXBT` = BTC, `ZEUR` = EUR, `DOT.S` = DOT). Both only read balances; both signatures are tested against the examples in the exchanges' documentation. Errors are `ExchangeError` with a plain sentence that never contains a key. Prices: `loaders.spot_eur` (Yahoo `<COIN>-EUR`), EUR = 1.
* **Refresh (`refresh.stage_crypto`).** Coinbase first, with the keys from Setup when there are any (`exchanges.coinbase_keys` -> passed to `coinbase_fetch.mjs` as its two environment variables; otherwise the user's environment variables, as before), then the database fallback, then `exchanges.load_blocks` for every active Binance / Kraken place; `exchanges.merge` adds the blocks up per coin. A place that cannot be read (or has no key yet) becomes a warning alert, the others go on. A block made of several exchanges is marked `mixed`, one read only through these APIs has `source: "api"`: the 5-minute quick refresh leaves both alone (only the full refresh knows all places).
* **Setup window (`setup.js`).** Every section's "add" form offers "a folder of CSV files" or "an API connection" (service list from `connectors`, fields from the table). Typed keys are posted once and dropped from the page. The window gets the class `wide` (`min(98vw, max(64vw, 86rem))`); rows wrap and nothing inside is wider than the window, so the only scroll bar that can appear is the vertical one of the pop-up when the content is taller than the screen. Problems are shown next to the Save button (`.spmsg`); needed fields (`REQUIRED`) are checked before posting and marked.
* **Text size (`wealthview.html`).** `--minfs`: 0 on the fixed ultra-wide screen (sizes unchanged), 11.5 px on every screen that scrolls; every `font-size` below 0.8 rem is written `max(var(--minfs,0px), …rem)`. Two-column screens (up to 1900 px wide) use `clamp(12.5px, 100vw/100, 17px)` as root size instead of `100vw/150`.
* **Installer (`installers/iss`).** Side pictures redrawn with the WealthView logo. `anim/wv-00.bmp … wv-35.bmp` (328 x 328, `dontcopy`, first in `[Files]`) are shown over the top square of the side picture on the first and the last page by a 90 ms Windows timer (`SetTimer` + `CreateCallback`, `AnimTick`); any problem switches the animation off and the still logo stays. `[Run]` is empty: the last page has its own tick box with an orange label (`BuildFinishStart`, `PlaceFinishStart`), and the Finish button starts `start-wealthview.ps1` (`NextButtonClick`, only after a successful setup, never silent).
* **Tests.** `tests/test_api_connectors.py` (19), `installers/tests/test_iss.py` (animation frames, finish box).

## 19. v1.23: local house values and fund sources
* **House or apartment in Germany (`data/finance/houseindex.py`, `assets.build_assets_block`).** The value follows the Deutsche Bundesbank's yearly residential price index of the kind of area the person picks in Setup (`area`: `big7` series `A.B10.N.G100.P0030.A`, `city` = 127 cities `...P0010.A`, `district` = all districts `...P0020.A`, `germany` = Destatis house price index `...P0050.A`; default `city`). One CSV request to `api.statistiken.bundesbank.de/rest/data/BBDY1/<series>` (no key; nothing but the series name is sent). The yearly values become quarterly ones (each year counts at mid-year, straight lines between, flat after the last year) and go through the existing `property_series`. Failure falls back to the Eurostat country index, then to a flat line. An own local price per m² (`price_per_m2` with `size_m2`) or an own `current_estimate` overrides the index; the basis text says which one was used. Immowelt and ImmoScout have no public interface and forbid automated reading, so they are not used. Destatis GENESIS needs a login, so it is not called.
* **Fund values (`data/ingest/fund_files.py`, `app/fund_tools.py`).** A fund takes its value, in this order, from the typed value, from the newest value found in the person's report folder (`folder`), from price x `units` by `isin` (`quotes.price_by_isin`: Yahoo search by ISIN), else at cost. Per file the reader tries a CSV table (date + value columns), then a labelled single number in the PDF text (`rule_extract`), then the local LM Studio model (`llm_extract`): its JSON answer is accepted only when the number stands in the text and the value is not more than 20 times what was paid in (a fund total instead of the person's share is refused with a note). PDF text comes from `pdftotext`, `pypdf` or a small built-in reader, in that order. Answers are remembered per file, size and time in `data/fund_reports_cache.json`, so the model is asked once per report. The report series are drawn into the fund's line (`assets.fund_series_points`). Nothing leaves the computer for this: the model is the LM Studio on this machine.
* **Privacy.** New outbound host: `api.statistiken.bundesbank.de` (series name only). Fund ISIN prices ask Yahoo with the ISIN. Report files are read locally.
